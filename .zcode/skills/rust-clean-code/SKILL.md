# Чистый Rust-код в swapnotif-rs

Универсальные правила чистого Rust + проектные решения swapnotif-rs.
Поведение задают спеки OpenSpec (`openspec/changes/<change>/specs/`),
реализация — этот документ. Расхождение кода со спекой — баг; спор о
требованиях — сначала спека, потом код.

## Контекст проекта (решено, не обсуждать в каждом PR)

- **Что это**: systemd **system**-сервис (root): опрос `/proc/meminfo`
  каждые 5 с, state machine Normal/Exceeded — edge-trigger на 80% с
  гистерезисом −5 п.п.; cooldown 5 мин гейтит **отправку**, но не
  генерацию события; незавершённое уведомление ретраится каждый цикл и
  отменяется при возврате в Normal. Атрибуция виновника по дельте
  `VmSwap` per-pid за окно 60 с (`(pid, starttime)` против
  переиспользования PID, кольцевой буфер снапшотов глубиной
  окно/интервал, группировка по cgroup v2). Доставка
  `org.freedesktop.Notifications.Notify` — подключение к сессионным
  шинам в момент события (logind + `/run/user/<uid>/bus`, fallback —
  перебор `/run/user/*/bus`). Готовность systemd — sd_notify `READY=1`
  в `$NOTIFY_SOCKET`, ручная реализация (~30 строк, без крейта).
- **Стек зафиксирован** (см. design D1/D2/D7/D8): `tokio`, `zbus`
  (+`zvariant`), `serde` + `toml`, `tracing`/`tracing-subscriber`
  (логи → stdout → journald). Парсер `/proc` — собственный, крейт
  `procfs` не используем; sd_notify — свой, крейт `sd-notify` не
  используем.
- **Один крейт bin+lib**: тонкий `src/main.rs` (composition root),
  библиотечные модули `monitor` (парсинг `/proc` + снапшоты),
  `attribute` (виновник), `notify` (сессии + доставка + формат
  сообщения), `daemon` (главный цикл + state machine триггера +
  sd_notify), `config` в `src/lib.rs`. Workspace/новые крейты — только
  с явным обоснованием.
- **Edition 2024**. Комментарии и doc-комментарии — на русском,
  идентификаторы — на английском.

## Главные принципы

- Сначала корректность, потом производительность: компилятор — союзник,
  не воюй с borrow checker — перепроектируй поток данных.
- Невыразимые некорректные состояния: state machine порога — enum
  (`Normal` / `Exceeded { pending }`), а не набор `bool` (порог,
  отправлено, cooldown). Edge-trigger с гистерезисом и cooldown —
  конечный автомат (design D5), тестируемый как чистая функция.
- `unsafe` — не ожидается в этом проекте (zbus и парсер /proc — safe
  Rust). Если появился — каждый блок с `// SAFETY:` и обоснованием,
  плюс отдельный вопрос на ревью «а зачем».

## Ownership и заимствования

- Owned-типы по умолчанию (`String`, `Vec<T>`, `PathBuf`); параметры на
  чтение — `&str`/`&[T]`; `impl AsRef<str>` — если нужно и то и другое.
- `Clone` — не пластырь от borrow checker: перестраивай код, чтобы
  времена жизни сходились естественно.
- Снапшоты атрибуции — `HashMap<(Pid, StartTime), u64>` в кольцевом
  буфере глубиной `окно/интервал`; дельта = текущий снапшот − старейший
  в окне по совпадению ключа, отрицательная дельта → 0. Дельты
  считаются без мутации старого снапшота.
- `Arc<Mutex<T>>` — не по умолчанию: по design D1 логика демона
  последовательна в одном tokio-таске (`monitor` → `attribute` →
  `notify` — прямые вызовы, каналы не нужны). Если появится вторая
  задача — обмен через каналы `tokio::sync` (`mpsc`/`watch`), не через
  разделяемое состояние.

## Обработка ошибок

- `anyhow` — на границе `main.rs` (старт демона, конфиг); в
  библиотечных модулях — `thiserror` с типизированными вариантами там,
  где вызывающий различает исходы: `AttributeError::ProcRead` vs
  `NotifyError::SessionUnavailable` vs `NotifyError::NotifyRejected`.
- Сообщения ошибок — на русском, с контекстом: какой pid/файл/шина.
- `.unwrap()` — только в тестах. `.expect("почему инвариант верен")` —
  лишь с документированным инвариантом (например, `SwapTotal` уже
  проверен выше по коду).
- Ошибка доставки нотификации в одну сессию не роняет демон: лог через
  `tracing` и продолжаем остальные сессии; фатальны только ошибки
  конфигурации/старта.
- `swap_total == 0` — не ошибка по спеке: состояние «swap выключен,
  ждём», не `Err`.

## Async-рантайм

- `tokio` — решение принято design'ом (D1: **один последовательный
  таск** с `interval`-циклом, демону не нужен конкурентный I/O).
  Не плодить конкурентность: новые `tokio::spawn` — только с
  обоснованием, ломающим последовательную модель.
- Файлы `/proc` крошечные — скан per-pid в обычном async-коде;
  `spawn_blocking` — только если профилирование покажет блокировку
  рантайма, заранее не вводить.
- Остановка демона (SIGTERM/Ctrl-C) — мгновенная (требование
  `Type=notify`/`Restart=on-failure`): `tokio::select!` между
  `interval.tick()` и сигналом shutdown, ветки cancellation-safe.
- zbus — async-native. Подключение к сессионной шине — **в момент
  доставки** события (D6); неудача одной сессии не блокирует остальные
  (лог, продолжаем); незавершённое событие ретраится на каждом цикле
  до возврата в Normal. Постоянные соединения и backoff не нужны,
  пока спека не потребует иного.

## Границы доверия (вместо FFI-раздела)

- FFI в проекте нет. «Внешние» данные здесь — `/proc/*` и сессионные
  шины; оба источника **не доверенные**:
  - парсер `/proc`: строки могут отсутствовать, быть обрезанными,
    содержать неожиданные числа (`VmSwap: garbage`), значения —
    превышать `u64`; размер файла ограничивать при чтении. Некорректная
    запись одного pid не ломает скан остальных;
  - данные из сессионной шины не разбираются и не интерпретируются
    (по proposal): только исходящий вызов `Notify`, ответы —
    «доставлено/не доставлено»;
  - имена cgroup и имена процессов не попадают в лог как доверенные
    идентификаторы — только как отображаемый текст.
- Числа из `/proc` парсятся строго: `/proc` отдаёт КиБ — единицы
  конвертируются в одном месте (`config`/`monitor`), без рассыпания
  конверсий по коду.

## Производительность

- Оптимизируем по измеримой проблеме (`criterion` + `perf`/
  `flamegraph`), не заранее.
- Горячий путь скана атрибуции: переиспользовать буферы (`String` с
  `clear()`), не аллоцировать на каждый pid лишнего (один путь-буфер на
  скан, а не форматирование строки пути на каждый pid).
- Итераторы вместо индексных циклов; `SmallVec` — не нужен, пока
  профилировщик не показал обратное.
- `#[inline]` — не пишем руками в прикладном коде, решает компилятор.

## Структура и зависимости

- Границы модулей — по домену и закреплены tasks.md: `monitor`
  (парсинг `/proc`, снапшоты), `attribute` (хранилище снапшотов,
  группировка, выбор виновника), `notify` (discovery сессий через
  logind, трейт `Notifier` + zbus-реализация, форматирование
  сообщения), `daemon` (главный цикл + state machine + sd_notify),
  `config`. Новые модули — только когда домен действительно новый.
- Зависимости внутри крейта: `main.rs` — единственное место, где
  собираются конкретные реализации; модули получают зависимости
  параметрами (трейты-источники данных, см. «Тесты»).
- `pub(crate)` по умолчанию; `pub` — только то, что реально нужно
  `main.rs`/интеграционным тестам.
- Конфиг (design D8): `#[serde(default)]` на каждом поле +
  `deny_unknown_fields` (опечатка в ключе — ошибка, а не молчаливый
  дефолт), валидация диапазонов (порог 10–99%, интервал 1–3600 с);
  невалидный конфиг — fail-fast выход с ненулевым кодом, молчаливый
  fallback на дефолты запрещён.
- Каждая зависимость в `Cargo.toml` — с комментарием-обоснованием;
  `default-features = false` + явные features где возможно (zbus,
  tokio, serde); новый крейт — сперва проверить, не решает ли `std`
  или уже подключённый крейт (прецедент: procfs и sd-notify отклонены
  в пользу собственных ~150/30 строк). `Cargo.lock` закоммичен всегда,
  правки `Cargo.toml` — в одном коммите с `Cargo.lock`.

## Тесты

- Решающая логика — чистые функции над распарсенными данными
  (`Snapshot`, `Attribution`): state machine порога (переход, устойчивое
  превышение, колебание в узкой зоне у порога, cooldown, старт без
  swap), выбор виновника (максимум прироста; «приложение не определено»
  при приросте < 50 МБ). Юнит-тесты — `#[cfg(test)] mod tests` в
  модуле.
- Границы системы (чтение `/proc`, logind, D-Bus) — за узкими
  трейтами (`Notifier` и источники снапшотов), в тестах подменяются.
  Главный цикл `daemon` тестируется с фейковыми источником данных и
  `Notifier`: событие → попытка доставки → ретрай → отмена. Никаких
  живых тестов с системной шиной, logind или реальным swap в CI.
- Парсер `/proc` — табличные случаи на реальных байтах + fixtures в
  `testdata/` крейта (`include_str!`): meminfo со `SwapTotal`/без него,
  `status` с `VmSwap`/без строки, обрезанная строка, мусор в поле,
  cgroup v2 путь с `::/`. Fixtures — синтетические, без реальных имён
  процессов и uid. Парсер байтов — property-based (`proptest`) на
  устойчивость к обрезанию.
- `mockall` — для моков трейтов границ.

## Стиль и вывод

- `///` — контракт сущности (что и зачем, со ссылкой на спеку при
  нетривиальном поведении); `//` — только нетривиальные решения.
  Закомментированный код — удалять.
- Константы порогов и окон — именованные (`DEFAULT_THRESHOLD_PCT`,
  `HYSTERESIS_PCT`, `COOLDOWN`, `ATTRIBUTION_WINDOW`,
  `ATTRIBUTION_MIN_DELTA`), дефолты `config` — единственный источник;
  дублирование константы в логике — находка на ревью.
- Вывод демона — только через `tracing` → journald; `println!` в коде
  демона — находка. Пользовательский вывод при ручном запуске —
  тоже `tracing`, уровни: старт/конфиг — `info`, событие нотификации —
  `info`, недоставленная сессия — `warn`, трасса скана — `debug`.

## Чек-лист ревью

Находка, если в коде есть:

- `unwrap` вне тестов без обоснования;
- `Clone`/`Arc<Mutex<_>>` как обход проектирования;
- блокировка рантайма (скан `/proc` вне `spawn_blocking`);
- доверие к данным `/proc` или сессионной шины (парсинг без обработки
  мусора, разбор ответов шины);
- конверсия единиц памяти (КиБ↔МиБ↔байты) вне `config`/одного места;
- новая зависимость без комментария-обоснования или с лишними
  features;
- magic numbers вместо именованных констант `config`;
- `pub` без нужды; `println!` вместо `tracing`;
- логика решения, зависящая от глобального состояния (не чистая
  функция);
- поведение за рамками спек текущего OpenSpec-change.

## Перед сдачей задачи

1. `cargo clippy --all-targets -- -D warnings` — чисто.
2. `cargo test` — зелёные.
3. `cargo fmt --check` — чисто (иначе `cargo fmt`).
4. Поведение сверено со спеками: `openspec validate --strict` для
   текущего change при правке спек.
5. При правке `Cargo.toml` — `cargo build` собирается, `Cargo.lock` в
   том же коммите.
6. Задачи по упаковке — дополнительно `dpkg-buildpackage` собирает deb
   (если `debian/` уже есть).

## Порядок применения

1. Прочитай спеки текущего change (`openspec/changes/`) — требования
   оттуда; этот скил — про «как», не про «что».
2. При правке: минимальный дифф; не рефакторить «заодно» то, что не
   просили.
3. При ревью: пройди чек-лист, верни список
   `путь:строка — запах — как чинить`, сортированный по важности.
