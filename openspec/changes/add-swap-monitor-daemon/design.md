# Design

## Context

Проект — свежий каркас bin+lib (`src/main.rs` тонкий, логика в `src/lib.rs`), спецификаций и кода пока нет. Целевая среда: Linux с systemd, cgroup v2 unified, KDE Plasma (демон уведомлений `org.freedesktop.Notifications` живёт на сессионной шине `user@<uid>.service`, сокет `/run/user/<uid>/bus`). Требование пакета: после установки deb демон включён и работает без дополнительных настроек — это зафиксировано в proposal и спеке `daemon-lifecycle`.

## Goals / Non-Goals

**Goals:**
- Один бинарник `swapnotif-rs`, работающий как system-демон: цикл мониторинга → state machine порога → атрибуция → доставка уведомлений.
- Работа «из коробки»: встроенные дефолты, опциональный `/etc/swapnotif/config.toml`.
- Минимальное дерево зависимостей: парсинг `/proc` — собственный, без крейта `procfs`.
- Тестируемость: чистые функции над распарсенными данными (`Snapshot`, `Attribution`) покрываются юнит-тестами без root и без реального D-Bus.

**Non-Goals:**
- Точная forensic-атрибуция через eBPF — эвристика «топ-прирост» достаточна для уведомления.
- GUI, действия по клику на уведомлении, звук/urgency-политики сложнее «normal».
- Мониторинг RSS/OOM, реактивные действия (oom-killer-подобные) — только наблюдение и уведомление.
- cgroup v1 как первоклассная поддержка (только деградация к группировке по `comm`).

## Decisions

### D1. Runtime: tokio (одна задача-цикл)
`zbus` асинхронный по своей природе; обёртка `zbus::blocking` всё равно поднимает внутренний runtime. Выбран один tokio-таск с `interval`-циклом: демону не нужен конкурентный I/O, вся логика последовательна.
*Альтернатива:* std-тред + blocking zbus — меньше зависимостей, но тот же runtime внутри zbus и хуже эргономика таймеров.

### D2. Парсинг /proc: собственный мини-парсер
Нужны всего 5 форматов: `/proc/meminfo` (2 строки), `/proc/vmstat` (2 ключа), `/proc/<pid>/status` (поле `VmSwap`), `/proc/<pid>/stat` (поле 22 `starttime`), `/proc/<pid>/cgroup` (строка `0::/...`). Файлы крошечные, парсер — ~150 строк с юнит-тестами на фикстурах. Это убирает тяжёлое дерево `procfs` (libc, стрейджи версий).
*Альтернатива:* крейт `procfs` — готовое решение, но тянет зависимости ради 5 полей.

### D3. Идентификация и окно атрибуции
Процесс = `(pid, starttime)`; кольцевой буфер снапшотов глубиной `окно / интервал` (дефолт 12 снапшотов при 60 с / 5 с). Дельта = `current - oldest в окне` по совпадению ключа; отрицательные дельты → 0. Умерший процесс просто не попадает в текущий снапшот. Переиспользованный PID получает другой `starttime` и потому не наследует след.
*Альтернатива:* экспоненциальные скользящие средние — точнее сглаживают, но сложнее объяснить и тестировать; для уведомления достаточно линейной дельты.

### D4. Группировка: cgroup v2 путь → юнит
Ключ группы — полный путь из `/proc/<pid>/cgroup` (`0::/user.slice/.../app-firefox.service`); отображаемое имя — последний сегмент пути без суффикса `.service`, fallback — `comm` процесса. На системах с cgroup v1 (нет строки `0::`) группы не строятся — группировка по `comm` (задокументированная деградация).
*Альтернатива:* парсить `desktop-file-id` из `systemd`-свойств юнита — точнее для иконок/имён, но добавляет вызовы D-Bus к systemd на каждый снапшот.

### D5. State machine порога
```
      fill < thr - hyst              fill >= thr
  +-------------+  Normal  +---------------------+
  |             v          v                     |
  |          [ Normal ] -----> [ Exceeded ]      |
  |             ^          |          |          |
  +-------------+          |          | pending notification
        ^                  |          v
        |   fill < thr-hyst|    [Deliver] --> cooldown gate
        +------------------+         |
                                     v
                       deliver cancelled if back to Normal
```
Событие живёт, пока состояние `Exceeded`; недоставленное уведомление ретраится на каждом цикле; при возврате в `Normal` до доставки — отменяется. Cooldown (монотонные часы) гейтит отправку, но не генерацию события.
*Альтернатива:* level-trigger с cooldown — проще, но на «пиле» вокруг порога штампует уведомления каждые cooldown-минуты; edge + гистерезис честнее к пользователю.

### D6. Доставка: прямое подключение root → user bus
При событии демон через logind (`org.freedesktop.login1`, system bus) получает сессии, фильтрует графические (`Type` = x11/wayland), сопоставляет uid → `/run/user/<uid>/bus`, подключается и вызывает `Notify`. Если logind недоступен — fallback: перебор `/run/user/*/bus`. Прецедент паттерна — `fwupd`. Ответы не разбираются: учитывается только факт успеха/неудачи вызова; полученные строки не используются (спека `desktop-notifications`).
*Альтернатива:* система из двух компонентов (system bus publisher + user-релей) — чище по привилегиям, но второй бинарник и второй юнит для задачи, которая решается одним вызовом.

### D7. sd_notify: ручная реализация
Готовность — запись `READY=1` в unix-датаграммный сокет из `$NOTIFY_SOCKET` (~30 строк, ноль зависимостей).
*Альтернатива:* крейт `sd-notify` — та же работа через зависимость.

### D8. Конфиг: serde + toml, fail-fast
`Config` со `#[serde(default)]` для каждого поля, `deny_unknown_fields` — опечатка в имени ключа это ошибка, а не молчаливый дефолт. Валидация диапазонов (порог 10–99%, интервал 1–3600 с и т.п.). Невалидный конфиг → выход с ненулевым кодом и сообщением в journald; systemd-цикл перезапуска ограничен `StartLimit` по умолчанию, и администратор сразу видит причину через `systemctl status`.
*Альтернатива:* молчаливый fallback на дефолты — прячет опечатку в пороге (например, `threshold = 800`), что для уведомителя опаснее явного отказа.

### D9. Упаковка deb
`debian/` с compat 13: минимальный `rules` (`dh $@`), юнит через `debian/swapnotif-rs.install` → `/usr/lib/systemd/system/`, бинарник в `/usr/bin/`. `dh_installsystemd` из стандартной последовательности сам делает `enable + start` в postinst и симметричный `disable + stop` в prerm/postrm — ручных maintainer-скриптов не требуется. Пример конфига — `debian/swapnotif-rs.examples`.
*Альтернатива:* ручные postinst с `systemctl --global enable` (для user-юнита) — отклонено вместе с user-размещением (см. proposal, развилка A/B).

### D10. CI релиза: GitHub Actions, deb-only
Workflow `.github/workflows/release.yml` на ubuntu-latest: тесты (`cargo test --locked`), затем `dpkg-buildpackage -us -uc -b` — тот же путь упаковки, что и локально (D9), поэтому `cargo-deb` в CI не используется (он не даёт `dh_installsystemd` и собрал бы пакет иначе, чем поставляемый). Триггеры: пуш тега `v*` (сборка + публикация) и `workflow_dispatch` с флагом publish (сборка без публикации; публикация только на теге — иначе явная ошибка, не тихий пропуск). Version-gate: номер тега обязан совпадать с версией из `Cargo.toml`, иначе публикация падает. Права: `contents: read` на сборку, `contents: write` — только у job'а публикации; release notes генерирует GitHub (`generate_release_notes`). Кросс-платформенные job'ы (Windows/macOS) не нужны — целевая платформа одна, Linux + systemd.
*Альтернатива:* `cargo-deb` — проще, но это другая упаковка, чем deb-пакет из D9; отдельный workflow build/test для PR — добавить, когда появится потребность в проверке PR до мержа.

## Risks / Trade-offs

- [Эвристика «топ-прирост» может указать не на истинного виновника (ядро выталкивало страницы разных процессов)] → честный fallback «приложение не определено» при малом приросте; в теле сообщения формулировка «наибольший рост», а не «виноват».
- [Root-демон подключается к сессионным шинам пользователей] → демон только отправляет `Notify` со своими строками; ответы/ошибки не разбираются, полученные строки не используются; сетевых сокетов нет (`RestrictAddressFamilies=AF_UNIX AF_NETLINK`).
- [hidepid / нестандартные монтирования /proc делают VmSwap части процессов нечитаемым] → недоступный процесс пропускается, атрибуция строится по видимой части; деградация логируется.
- [Невалидный конфиг + `Restart=on-failure` = цикл рестартов] → встроенный systemd `StartLimit` останавливает цикл, причина видна в `systemctl status`/`journalctl`.
- [Менеджер уведомлений существует только пока жива графическая сессия] → недоставленное событие ретраится до сброса порога; отсутствие сессий — не ошибка.
- [Разница между «свап занят» и «системе плохо»] → осознанный выбор триггера по заполненности (см. proposal); скорость обмена в теле сообщения даёт контекст.

## Migration Plan

1. `cargo deb` / `dpkg-buildpackage` собирает пакет; установка на целевой машине.
2. Проверка из коробки: `systemctl is-active swapnotif-rs` → active; `journalctl -u swapnotif-rs` — чистый старт.
3. Приёмочный тест триггера: во временной тестовой конфигурации снизить порог (например, до 5%) и аллоцировать память тестовым процессом → уведомление появляется в Plasma.
4. Откат: `apt remove swapnotif-rs` — демон останавливается и отключается стандартными средствами; система без изменений (демон ничего не пишет вне journald и `/etc`).

## Open Questions

- Иконка уведомления: сейчас кандидат — стандартное имя `drive-multidisk` (или `dialog-warning`); не влияет на спеки и задачи, выбирается при реализации.
- Точная формулировка summary/body (русские строки) — финализируется при реализации; состав данных зафиксирован спекой.
